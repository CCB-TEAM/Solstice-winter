# 设计：UI（WPF + Nodify）

状态：`PROPOSED`（骨架与交互已定，未实现）
依据：D1（WPF + Nodify）、D8（宽松拖拽 + 编译校验）、D9–D12（见 [可行性评估](可行性评估.md) §5）

---

## 0. 三条事实先摆着（它们决定 UI 长什么样）

1. **cooked 资产里没有布局**：节点位置、注释、折叠状态在 cook 时被剥掉。
   所以「打开就是原图」做不到——布局是算出来的，手动位置只能进侧车文件。
2. **一个 ubergraph 是 N 段**（实测 `BP_Logic` 170 段、50 个事件入口），
   在 UE 里这就是 50 张事件图。一张画布画完是不现实的。
3. **我们的模型是嵌套 AST**（`IfNode{Then, Else}`），UE 的图是**平铺 exec 链**
   （Branch 有两个 exec 出脚）。两者要一层投影，方向决定编辑自由度。

## 1. 骨架：按 UE 原逻辑

```
┌────────────────┬──────────────────────────────────┬──────────────┐
│ My Blueprint   │            画布                   │ 详情          │
│                │                                  │              │
│ ▾ 图表          │   [Event BeginPlay]              │ 节点：Branch  │
│   • 事件图      │        │ exec                    │ 条件：IsValid │
│     ├ BeginPlay│   [Set X] ─▶ [Branch]            │ 类型：bool    │
│     ├ Tick     │              ├ true  ─▶ [...]    │ 来源：本资产  │
│     └ ...(50)  │              └ false ─▶ [...]    │              │
│ ▾ 函数          │                                  │ 引脚          │
│   • GoHome     │                                  │  exec  ▶     │
│   • ...        │                                  │  cond  ○     │
│ ▾ 变量          │                                  │              │
│   • EntryPoint │                                  │              │
├────────────────┴──────────────────────────────────┴──────────────┤
│ 诊断  ✅ 字节一致    ⚠ 2 个引脚 unknown    入口点 50/50    ⟳ 已校验 │
└──────────────────────────────────────────────────────────────────┘
```

要点：

- **左侧是 UE 的 My Blueprint 树**：`图表（事件图 + 每个函数）` / `变量`。
  事件图下**只列有入口的段**（`BP_Logic`：50 个事件，不是 170 段）——
  段名来自调用点反查（stub 名 → `EX_IntConst` → 偏移），不是从段体猜的。
- **内部段不占列表位置**：没有入口的段（共享尾、switch case 体）在图里以
  「跳转目标块 `#37`」的形式出现，点开才展开成一张子图。
- **主画布一次只画一张图**（当前选中）。170 段不会同时加载。
- **函数与事件图是同一套渲染**：区别只在「事件图 = ubergraph 的一段」还是「普通函数」。
- **块图只读**：还原不出结构的函数（实测 3 个）明确标「此函数无法结构化，只读」，不给假象。
- 底部诊断条常驻：字节一致性、unknown 引脚数、入口点计数、最近一次校验时间。

## 2. 投影：AST ↔ 平铺图

### 2.1 正向（读）：`KNode` → 节点 + 引脚

| 模型 | 画成 | 引脚 |
|---|---|---|
| 顶层 `KNode` 序列 | 一条 exec 链（左→右） | 每个节点 `exec in` / `exec out` |
| `IfNode` | `Branch` | `cond`（数据）、`then` / `else`（exec 两个出脚） |
| `LoopNode` | `While` | `cond`、`body` 出脚 + 回边 |
| `BottomLoopNode` | `DoWhile` | `body` + `cond` + 回边 |
| `AssignNode` / `AssignBoolNode` | `Set <变量>` | `exec in/out` + 值输入 |
| `CallNode`（纯） | 数据节点 | 输出脚 → 下游输入脚 |
| `CallNode`（有 exec） | 调用节点 | `exec in/out` + 参数脚 |
| `ReturnNode` | `Return` | `exec in` |
| `PushFlowNode` / `PopFlowNode` | 异步标记节点 | 只读展示目标段 |
| `RawNode` / 未结构化 | 灰色不透明节点 | 无引脚，双击展开原始字节 |
| `BlockGraphNode` | 显式块图 | 块之间用 goto 边连 |

### 2.2 反向（写）：平铺图 → 字节码

**编辑过的函数走新路径**：平铺图 → 线性化 → 两遍算偏移 → 字节码。

- 线性化：按 exec 边的拓扑顺序排（无环时就是链；有环必须有显式 `While/DoWhile` 节点）。
- 跳转：非顺序后继发 `EX_Jump`；`Branch` 的 else 发 `EX_JumpIfNot`。
- 数据流：纯节点按依赖顺序内联成嵌套表达式（与现有 AST 编译器同一套 `ToExpr`）。

### 2.3 混合真相的硬规则

| 函数状态 | 真相 | 编译器 |
|---|---|---|
| 未编辑（干净） | AST（反编译得到的那棵树） | 现有 `KismetCompiler`，保 8115/8115 逐字节 |
| 编辑过（脏） | 平铺图 | 新的图编译器 |

- **没有改动就不切换真相**：打开→保存不动，字节必须与原始一致（这是信任的底线）。
- 切换只发生一次（第一次真正改动该函数时），之后该函数一直走平铺图。
- 平铺图的产物必须能被重新反编译并再次投影（否则用户改完就再也打不开了）。
- **保存闸门（D15′）**：写盘前把刚产出的函数重新反编译一遍，
  退化到块图或无法投影成平铺图 → **拒绝写盘并报错**。
  宁可保存失败，也不产出一个「打不开」的资产——这和入口点错位拒绝写盘是同一种保护。

## 3. 节点外观

- **exec 引脚**：三角/箭头，白；**数据引脚**：圆，按类型配色（bool 红、int 青绿、float 绿、string 品红、object 蓝、struct 深蓝、unknown 灰）。
- **类型来自哪**：引脚 hover 时显示「来源」——`jmap 签名` / `usmap 结构` / `资产属性表` / `推断`。推断不出来的画灰点并标 `unknown`（只读，不许连）。
- **常量内联**：`Set X = 7` 的 `7` 直接在节点上改，不弹窗。
- **不透明节点**：灰底 + `?` 角标，双击展开只读的原始字节/反编译文本（D11）。
- **选中态**：右侧详情显示参数、类型、来源、谁在调用（`Referencers` 索引，O(1)）。

## 4. 交互

| 动作 | 行为 |
|---|---|
| 拖 exec 出脚到空白 | 弹候选面板，按「本资产函数 → 同继承链 → `/Script`」排序，可按名字搜 |
| 拖数据出脚到输入脚 | 只允许类型兼容；不兼容当场拒（不让落线） |
| 拖节点 | **只改位置**，写侧车，不触发编译 |
| 删节点 | 前驱 exec 直连后继（保链）；删 `Branch` 需明确选 `then` 或 `else` 承接 |
| 框选 / 复制粘贴 | 复制含数据上游（纯节点）与 exec 下游一段，粘贴时重映射局部变量 |
| 双击常量 | 内联编辑，失焦即提交 |

拖拽语义按 D8：**宽松**——允许任意重连（含合并两条 exec），只拦类型层与结构层，不拦语义层。

## 5. 校验与提交（D12）

```
编辑 → 300ms 防抖 → 后台编译 + 字节校验 → 结果回填（带版本号）
                                              ↓ 版本号不匹配就丢弃
保存 → 强制同步：所有脏函数重新编译 + 入口点校验 + 写盘
```

- **竞态**：每次编辑递增 `graphVersion`；后台结果回来时版本不一致就丢弃，不覆盖 UI。
- **三层校验**（D8）：类型层在落线时拦；结构层在后台编译后拦；语义层不查。
- **差异视图（D16）**：只给**节点级**——exec 顺序与跳转目标的前后对比（增/删/改/重连）。
  不做字节 hex diff：准但没人看得懂，等于没提示。
- **事务**：每次编辑前存字节快照；后台校验失败自动回滚并高亮出错节点路径。
- **undo/redo**：Nodify 自带基础，但**撤销粒度 = 一次事务**（含位置与结构），不是每次鼠标移动。

## 6. 自动布局与位置

- **分层布局**：exec 链左→右（x 递增），数据上游在下方（y 负向），分支的 then/else 上下分叉。
  纯节点（数据）优先放在使用它的节点正下方，避免长边穿越。
- **位置侧车**：`<项目>/.solstice-winter/layout/<资产名>.json`
  ```json
  { "graphs": { "ExecuteUbergraph_BP_Logic#12": { "nodes": { "3:Call:GoHome": [420, 160] } } } }
  ```
  键 = `段序号:节点类型:标题`，并附一个短指纹（标题 + 参数数量）。
  **找不到就自动布局**——结构改动会让键漂移，这是可接受的（位置本来就不是原图）。
- **不做的事**：不试图还原原作者布局（做不到，见 §0）。

## 7. 性能

| 场景 | 规模 | 处置 |
|---|---|---|
| 一张事件图 | 10~20 个节点 | 直接渲染 |
| 一个函数 | 几十~几百个节点 | 虚拟化：只渲染视口内 |
| 切换图 | 170 段之一 | 只反编译当前段，不预载全函数 |
| 后台校验 | 45 KB 的 ubergraph | 单线程、可取消；保存时同步 |

---

## 8. 边界（明写在 UI 上，不藏在文档里）

- 布局是自动生成的，不是原作者那张图。
- 语义层不校验：拖错了不报错，只在「差异视图」里显示 exec 顺序变化。
- `unknown` 类型的引脚不可连。
- 不透明节点里的逻辑不可编辑（只读展开）。
- 编辑过的函数不再保证与原始字节一致（未编辑的仍然保证）。
