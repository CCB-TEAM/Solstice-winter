# 可行性评估：cooked 蓝图节点编辑器（多数据源 + 强上下文）

状态：`PROPOSED`（结论基于本机实测数据，非推测；未验证的部分逐条标 `UNVERIFIED`）
日期：2026-11-07

---

## 0. 结论

**可行，而且地基比预期厚。** 读 → 改 → 写这条最危险的链路已经有硬证据：
`solstice-kismet` 对 28 个 Logic 资产 + 2053 个 Cards 资产共 **8115 个函数**做到了
「反编译 → 重新编译 → 序列化」**逐字节一致**（HANDOVER.md §二）。

但有一条必须提前说清，它决定产品承诺怎么写：

> **cooked 资产里没有 EdGraph。** 节点位置、连线、注释、节点类型名、折叠状态，
> 全部在编辑器专用数据里，cook 时被剥掉，只剩 `FunctionExport.ScriptBytecode`
> 这个线性表达式数组。
>
> 所以任何「仿 UE 节点编辑器」的视图都是**从 AST 重建的视图**，不是原作者画的那张图：
> 节点位置必须自动布局，位置只能存在**侧车文件**里（写不回资产），
> 同一个函数每次重建出来的图长得一样，但不是原图。

这不影响「能编辑」，但影响三件事：UI 文案不能暗示「还原原图」；布局算法是必需品不是装饰；
侧车文件是项目数据的一部分，要纳入版本管理。

真正的成本集中在三处，且**都不在解析层**：

| 成本中心 | 难度 | 为什么 |
|---|---|---|
| 跨资产上下文索引 | 中 | 要自己扫全部蓝图资产补出 BP 函数签名/类继承/变量类型，jmap 只覆盖 `/Script` |
| ubergraph 任意重排 | 高 | 入口偏移烘在**调用点常量**里，段内移动会让所有事件错位；现有闸门只允许段尾追加 |
| 新建事件 / 新建函数 | 高 | 包结构手术：Export 表 + 名字表 + 事件 stub + ubergraph 段 + 调用点常量，五处同时改 |

最大的未知不是「能不能解析」，而是「改完在游戏里对不对」：整条链路目前只证明了**字节层**，
没有任何一次运行时验证（SKILL.md §7 也这么写）。

## 2. 五个可行性判断

### 2.1 多数据源统一：可行，成本低

按「**事实的粒度**」分层，不按文件格式分：

```
pak / 散文件 ──┐
assetregistry ─┼─→ PackageStore   包级：某个 .uasset/.uexp 的字节从哪来
usmap ─────────┼─→ TypeSchema     类型级：结构体/类/枚举成员与继承（原生）
jmap ──────────┼─→ SymbolTable    符号级：/Script 函数签名 + 对象表
资产本体 ──────┴─→ ProjectIndex   项目级：/Game 蓝图函数签名、类继承、变量类型、跨资产引用
```

冲突时的**权威顺序**（默认，可改）：**资产本体 > usmap > jmap > registry**。
理由：资产本体是唯一「写回去会影响运行时」的事实源；usmap 是引擎侧的编译期真值；
jmap 是运行时对象转储（可能缺、可能旧）；registry 只是缓存（vision.md §7 已指出这点）。

### 2.2 节点图重建：可行，成本中

映射规则是机械的，因为蓝图编译器本身就是「图 → 线性字节码」：

| 图元素 | 字节码里的对应物 | 重建方式 |
|---|---|---|
| exec 链 | 顶层 `KNode` 顺序 + `IfNode`/`LoopNode` 结构 | 直接映射 |
| 纯节点（数据） | 嵌套的 `CallArg` / 字面量 `KArg` | 每个嵌套调用 = 一个节点 |
| Get 变量节点 | `PointerArg`（`FFieldPath` + `ResolvedOwner`） | 按需合成 |
| Set 节点 | `AssignNode` / `AssignBoolNode` | 直接映射 |
| 引脚类型 | **不在字节码里** | 见下 |

**引脚类型是唯一需要推断的东西**，但有确定的来源，不需要猜：

1. 调用的引脚 ← jmap 签名（`/Script`）+ ProjectIndex（`/Game`，自己扫出来）
2. 变量引脚 ← 函数/类的 `LoadedProperties`（`FProperty` 带完整类型，含容器内层）
3. 结构体成员 ← usmap；**蓝图结构体（`S_*`）不在 usmap**，但 `UserDefinedStructExport` 里有，从资产本体读
4. 字面量 ← opcode 自身（`EX_IntConst` → int …）
5. 中间值（运算结果）← 被调函数的返回类型，逐层传播

代价：`RawArg` / `RawNode`（`EX_SwitchValue` 等尚未结构化的指令）在图上只能显示成
「不透明节点」，引脚不可展开。这类指令在 8115 个函数里的占比已有统计口径（`kismet_verify`），
可以量化而不是含糊。

### 2.3 编辑语义：分层可行，三档成本差一个数量级

| 档 | 能力 | 可行性 | 关键约束 |
|---|---|---|---|
| A | 参数/常量改、段尾追加调用 | **已验证**（MCP 12 个工具全跑通） | 占位参数（text/struct/array/map/set）仍需真实载荷 |
| B | 既有函数内任意插/删/换、重连线 | **可行**（普通函数） | 跳转是字节偏移，编译器已两遍重算；结构必须合法 |
| B′ | ubergraph 段内任意重排 | **未验证，可做但要新层** | 入口偏移 = 调用点里的 `EX_IntConst`；段内移动必须同时改写所有调用点常量，并复核 `PushExecutionFlow` / `ComputedJump` 目标 |
| C | 新建事件 / 新建函数 / 新建变量 | **高风险** | Export 表 + 名字表 + stub + 段 + 调用点，五处同时改；UAssetAPI 加 Export 的索引重排没有现成保证 |

**绕过 C 的实用办法**：不新建事件，而是**复用**资产里已存在的、没有调用点的 stub（或用未使用的自定义事件），
改它的名字与段内容。这一步把「包结构手术」降级成「改字节码」，风险差一个数量级。
建议把 C 作为研究 spike，不作为第一里程碑。

### 2.4 「超强上下文」的真实来源

不是数据源多，而是**索引**：扫一遍 2137 个蓝图资产，建出

- 类 → 父类链（`SuperStruct`），可跨资产
- 类 → 变量（名字/类型/默认值/是否可编辑）
- 类 → 函数（名字/参数与返回类型/flags/是否有字节码/字节码长度）
- 资产 → 引用（Import 里的对象路径），即「谁调用了谁」
- 蓝图结构体 → 成员（补 usmap 的缺口）

有了它，拖引脚时能按「参数类型 + 是否 exec + 是否同一继承链 + 是否本资产」过滤出候选函数，
覆盖 `/Script` 与 `/Game` 两侧。**这正好解掉现有工具链的两个既有边界**
（SKILL.md §7：`functions.json` 只有 `/Script`；`objects.json` 的 `super` 恒为 null）。

2137 个资产 / 10.8 MB，全量扫描是秒级到十几秒级的事，可以每次启动重建，也可以落 SQLite 缓存。

### 2.5 验证：字节层已有，运行时没有

现有验证是四层里的三层：结构化还原 → 回编译 → 字节比对 → 重开读回。
缺的是第四层「运行时正确」。三个可选通道：

| 通道 | 成本 | 强度 |
|---|---|---|
| 字节级 + 重开校验（现状） | 0 | 只能证明「没写坏」 |
| 打进 mod pak 进游戏实测 | 低（一次性） | 最强，但只能抽检，不可回归 |
| 接 KARDS 的 Kismet→C# 解释器跑函数（`ccb-analysis` 那套） | 高 | 可回归、可批量，但解释器自身要可信 |

建议：**A 档每次必跑，B 档在里程碑处人工抽检，C 档作为长期能力**。
任何文档不得把「序列化成功」写成「运行时正确」（Solstice AGENTS.md 的硬规则）。

## 3. 风险表

| # | 风险 | 触发条件 | 后果 | 处置 |
|---|---|---|---|---|
| R1 | 新建事件/函数改坏包结构 | 走 C 档 | 资产打不开或运行时崩 | 先做复用 stub 路线；C 档单独开研究分支，输出必须过「重开 + 全量 verify」 |
| R2 | ubergraph 段内重排导致事件错位 | 走 B′ 档 | 事件跳到指令中间（`ComputedJump` 落进操作数） | 重定位层 + 入口点全量校验；校验失败回滚；`BP_Logic`（170 段 / 50 入口）当压测 |
| R3 | 类型推断错 | BP 结构体成员、delegate、interface | UI 显示错引脚、编辑期类型不匹配 | 推断不出就标 `unknown`，不猜；引脚拖拽时拒绝不匹配 |
| R4 | pak 直读 | 想省掉 FModel 导出步骤 | 需要 v11 解析 + AES key + Oodle 解压 | 见 §5 Q3；短期用导出目录 |
| R5 | 节点位置无处存 | 用户期待「打开就是原图」 | 认知落差 | UI 明确「自动布局」，位置进侧车文件 |
| R6 | 版本漂移 | 目标游戏换 UE 版本 | `EX_Let` 形态、`FFieldPath` 等假设失效 | 只声明 5.6 已实测；版本差异集中在一层适配 |
| R7 | 占位参数 | text/struct/array/map/set 参数 | 生成的字面量不可用 | 已有 `??` 标记，UI 必须显式提示并要求填真实载荷 |
| R8 | 运行时未验证 | 任何「能用」的承诺 | 静默错误（ccb-analysis 05 的教训：容错是最大错误源） | 把「字节一致」与「运行正确」在 UI 上分成两个徽标 |

## 4. 模块草案（新工具 = 索引 + 图 + 受控编辑，解析复用现有库）

```
Sources        pak | loose dir | assetregistry.bin | usmap | jmap
                 ↓
ProjectIndex   跨资产符号/类型/引用索引（SQLite 或内存）
                 ↓
Workspace      包级读写（UAssetAPI + Solstice.Kismet），多包事务、脏标记、回滚
                 ↓
GraphModel     AST → 节点/引脚/连线 + 类型推断 + 自动布局（位置进侧车）
                 ↓
EditOps        受控编辑：Insert/Delete/Replace/Rewire，每步过字节校验与入口点闸门
                 ↓
UI             画布 + 属性面板 + 候选函数面板 + 差异/校验面板
```

与现有仓库的关系：`solstice-kismet` 是 Workspace 的实现基础（不重写）；
`Solstice.AssetRegistry` / `solstice-jmap` / `solstice-pak` 分别填 Sources 的一格；
新增的是 **ProjectIndex / GraphModel / EditOps / UI** 四层。

## 5. 已定案的决策（2026-11-07）

| # | 决策 | 为什么 | 代价（明写，不粉饰） |
|---|---|---|---|
| D1 | **WPF + Nodify 桌面端**（Windows only） | 单语言、零 JS、能直读磁盘与 pak；Nodify 是 .NET 生态里唯一成熟的节点画布 | 放弃跨平台与浏览器分发；WPF 的字体/缩放不如浏览器细腻 |
| D2 | **第一里程碑 = B 档**：既有函数内任意插/删/换 + 重连线 | 普通函数已证明可行（编译器两遍重算字节偏移）；事件图是蓝图的重心，只读没意义 | 必须新写 **ubergraph 重定位层**：段内移动要同时改写所有调用点常量并复核执行流栈目标，风险集中在这里 |
| D3 | **自写 v11 pak reader**（不引 CUE4Parse） | 依赖面最小；pak 是「数据从哪来」的地基，自己掌握才好排查 | 要自己处理 AES 索引、Oodle 解压（仍需外部原生 DLL）、v10+ 编码条目；写路径暂时不做 |
| D4 | **KARDS 专用 + 游戏 profile 抽象** | 事实以 KARDS 实测为准，但版本/路径/密钥集中到一个 profile，换游戏只加一份配置 | 多一层薄抽象；profile 字段不够时还得改核心 |
| D5 | **上下文 = VFS + mmap + 懒解析 + 落盘索引**，目标是 O(1) 查表 | mount 只读文件表（索引 633 KB，几十毫秒），一个资产正文都不解析；按路径/按短名/按类/按被引用全是字典命中 | mount 本身仍是 O(n)，省不掉；索引缓存需要指纹与失效逻辑；mmap 只解决未压缩条目，Oodle 仍要解压 |
| D6 | **ubergraph 先做重定位 spike，过了再全量支持** | 段内移动的风险是「事件跳进指令中间」，只能靠实测说话；`BP_Logic`（170 段 / 50 入口）是压测靶子 | 多一个实验阶段，结论未知；不通过就自动降级为「整段级重排」 |
| D7 | **散文件为默认保存，pak 导出可选（v3）** | 实测游戏里两个真实 mod pak 都是 v3 / 不压缩 / 一对 uasset+uexp，`solstice-pak` 已覆盖该形态 | 不做 v11 writer（回写 1.17 GB 索引不值）；要维护「脏集 → 散文件 / pak」的归属 |
| D8 | **拖拽宽松 + 编译校验** | 用户要自由度：任意重连，由编译期兜住 | **语义层不校验**——拖错了不报错，运行时才看出行为变了；因此必须配事务回滚与前后差异视图 |
| D9 | **混合真相**：未编辑走 AST（保 8115/8115），编辑过的切平铺图 + 新编译器 | 既不许「任意重连」被 AST 的嵌套结构限制，也不拿已证明的保真去冒险 | 两套真相要同步；新编译器要单独验（线性化 + 跳转回填）；**没改动就绝不切换** |
| D10 | **图的组织照 UE 原逻辑**：My Blueprint 树 + 每函数/每事件一张图 | `BP_Logic` 170 段不可能一张画布；按图隔离也让脏标记、校验、撤销都按函数算 | 看不到「事件之间」的跳转全貌；跨段跳要另给指示 |
| D11 | **不可读节点画成不透明块**，双击展开原始字节 | `RawArg` / `EX_SwitchValue` 目前没结构化，藏起来会让人以为那段逻辑不存在 | 多一层展开交互；不透明块里的逻辑不可编辑 |
| D12 | **校验防抖异步 + 保存时同步** | 45 KB 的 ubergraph 每次按键都编译会卡死 | 要处理「后台结果回来时图又变了」的竞态（版本号丢弃）；错误提示有延迟 |
| D13 | **反编译器升级成图 IR**：节点带字节区间 + 内容指纹 + 显式 exec/data 边 + 具体引脚类型 | 编辑器要的定位、重定位、身份、拖线类型判断，树形结构一样都给不了 | 要改 `KismetDecompiler` 的输出契约（与现有调用方兼容要小心）；与 D6 的 PushFlow 符号化同属一个 fork |
| D14 | **左侧树只列有入口的段**（`BP_Logic`：50 个事件，不是 170 段） | 120 段是共享尾/switch case 体，当事件列出来是错的；段名用调用点反查，不用 `GuessLabel` 猜 | 内部段要在图里以「跳转目标块」呈现，点开才展开，多一层交互 |
| D15 | **块图只读**（实测 3 个函数退化成块图） | 结构化失败就是失败，给个能编的假象更糟 | 那 3 个函数永远只能看；且必须配 D15′ 的保存闸门，否则我们自己会把函数变成只读 |
| D16 | **差异视图只给节点级**（exec 顺序 + 跳转目标的前后对比） | 字节 hex diff 准但没人看得懂，等于没提示 | 看不到字节层面的连带改动；异常排查要靠诊断条与日志 |

| D17 | **第一版编辑算子 = 改常量 / 改调用参数 / 替换调用 / 重连线**（不做删除节点、插入新调用） | 四个算子都只动「已有结构的局部」，不新增节点，风险最小 | 不能增删节点，也就不能真正改变控制流形状；「插入调用」要等候选面板与类型过滤 |
| D18 | **保存：只写新目录，可选覆盖导出目录** | 原文件默认不动，改坏可重来 | 多一个危险开关与确认流程；覆盖后没有回滚 |
| D19 | **现在把 jmap 并入索引**，权威顺序：资产本体 > usmap > jmap > registry | 引擎函数的参数名/返回类型现在只有 `arg0`，并入后拖线才可能有意义 | 索引构建多一步（13k 条签名），缓存文件变大 |
| D20 | **位置侧车等编辑一起做** | 位置只在能编辑时才有意义；现在自动布局够用 | 每次重排都会跳，大图无法手工整理 |

| D21 | **把 UEBlueprintGraphViewer 的反编译器移植到 UAssetAPI**（不换栈） | 编辑路径必须走 UAssetAPI（CUE4Parse 不能写），双栈会让「节点 ↔ 字节码」映射对两遍 | 非 UI 代码 7.4k 行、约 282 处 CUE4Parse 类型引用要译；估计 4–5k 行有效移植 |
| D22 | **第一版只移「控制流 + K2 节点 + 引脚」**，宏与 Timeline 后置 | If/Switch/Cast/变量 Get/Set 是「看起来像 UE」的关键；宏是加分项 | 宏内联的 For Each Loop 等仍显示成展开后的字节码节点 |
| D23 | **自动布局改用 Microsoft.Msagl**（与参考项目一致） | 自研分层布局在上百节点时交叉严重；Msagl 是现成的 Sugiyama | 多一个依赖（MIT，已 vendored 到 `.nuget-local`） |

**D15′（由 D9 + D15 推出的硬闸门）**：写盘前把**自己刚产出的**函数重新反编译一遍，
如果退化成块图（或无法再投影成平铺图），**拒绝写盘并报错**。
理由：编辑过的函数走平铺图，一旦产物不可再读回，用户改一次就被锁死；
这和「入口点错位拒绝写盘」是同一种保护——宁可保存失败，也不产出一个打不开的资产。

配套约束（由 D3/D4 推出，已落到代码里）：

- **AES key 不落仓库**：从 FModel 的 `%APPDATA%\FModel\AppSettings.json` 读取
  （`PerDirectory[<游戏目录>].AesKeys.mainKey`），`GameProfile` 负责这件事。
- **Oodle 不随仓库分发**：`Oodle.cs` 按「显式路径 → 环境变量 `SOLSTICE_WINTER_OODLE` → 程序目录 → 已知本地工具链」找
  `OodleLZ_Decompress`，找不到就抛异常并列出候选，不静默返回压缩数据。
- **目标 pak 的真实形态**（实测，别再猜）：`kards-Android_ASTC.pak` = 1,170,194,667 字节 /
  version **11** / 索引 **AES-256-ECB 加密** / 条目 **Oodle** 压缩 / 无 IoStore。

## 6. 工程约束（踩出来的，别重复踩）

| 约束 | 现象 | 处置 |
|---|---|---|
| MSBuild 并行节点在本机会失败 | `dotnet build` 报「生成失败 / 0 个错误」，`_GenerateRestoreProjectPathWalk` 失败，日志里没有任何 error | **一律加 `-m:1`**。这条已写进 INDEX 与交接说明 |
| pak footer 不是末尾 44 字节 | 按老布局读会得到 magic=0、version=0 | footer = `[GUID 16][加密标志 1]` + 老字段 + `5×32` 压缩方法名；magic 在 `len-204` |
| 压缩方法名是定长 32 字节缓冲 | 按 FString 读会跑飞 | 定长读、`TrimEnd('\0')`、空槽跳过 |
| 中文环境下 `dotnet build -v q` 会吞掉错误 | 只显示「0 个错误」 | 用 `-v n` 或看完整日志；判断成功与否以**退出码**为准 |
| **主索引里的 bool 是 4 字节** | 按 1 字节读会让后续字段整体错位 3 字节 | UE 的 `FArchive` bool 是 int32；`ByteCursor.ReadUInt32Bool` |
| **加密块的起点不需要 16 字节对齐** | 按「对齐起点再切片」解出垃圾 | 从块起点读 `align16(len)` → 整段解密 → 取前 len |
| 单块条目的块大小可能是 0 | 按块大小判压缩会把压缩条目当原始数据返回 | `IsCompressed` = 「有方法且有块」 |

> pak 的完整实测布局（含 v10+ 编码条目位域、单块省略块长、残留字节判据）见
> [src/SolsticeWinter.Pak/PakArchive.md](src/SolsticeWinter.Pak/PakArchive.md) 与
> [PakInfo.md](src/SolsticeWinter.Pak/PakInfo.md)；本文不再复述细节，只记会重复踩的坑。
